## Принципы (обязательны для каждого этапа)

1. **Сначала документ — потом код** (§21): правка `ARCHITECTURE_PLAN.md` (§5 модели / §6 контракт / §16 решения) и `docs/API_V2_CONTRACT.md` — первым коммитом этапа.
2. **v2-стиль API**: Problem Details, `Idempotency-Key` на мутации-действия, ETag/If-Match на мутируемых ресурсах, cursor-пагинация, RBAC через `require_role`.
3. **Тесты**: pytest + обновление contract-fixtures (`tests/fixtures/v2/*.json`, openapi-фикстура) + Playwright на UI-флоу. Юнит-тесты на деньги/цены — обязательны.
4. **Завершение этапа**: `make test` зелёный → запись в `PRICE_WEB_PROGRESS.md` → деплой по плейбуку (прод: PM2, `source .env`, только из git).
5. Один этап = одна сессия/PR. Размеры: S ≈ 1 сессия, M ≈ 1–2, L ≈ 2–3.

## Этап 1. Фильтры и поиск в истории заказов — S ✅ (28.09.2026)

**Цель:** клиент находит заказ по номеру, позиции, комментарию, дате, сумме.

- **Backend** (`GET /api/v2/orders`): опциональные `q`, `date_from`, `date_to`, `min_total`, `max_total`, совместимые с cursor-пагинацией. `q` — по `seq`, SKU/названию позиций, комментарию. Репозиторий: ILIKE + join по позициям; индексов `seq`/`created_at` достаточно (объём заказов мал).
- **Frontend** (`pages/orders/index.vue`): панель фильтров (поиск, дата-диапазон, сумма) с синхронизацией в URL — паттерн уже реализован в каталоге (восстановление при F5).
- **Канон:** §6 + API_V2_CONTRACT.
- **Приёмка:** e2e — поиск по номеру и по SKU находит заказ; фильтры выживают F5; пустой результат — корректная заглушка.

## Этап 4. Счёт на оплату — L ✅ (30.09.2026)

> Выполнено: канон §5.2/§6/§10/§16 п.40, миграция 0023 (`invoices` + реквизиты
> организации + `FileAsset.order_id`), 6 эндпоинтов v2, Celery-рендер PDF,
> панель менеджера, карточка клиента, страница реквизитов организации.
> Проверено на проде: выставление, идемпотентность, `If-Match`, PDF байтами,
> изоляция по клиенту. Подробности — `PRICE_WEB_PROGRESS.md` 30.09.
> Открыто: реквизиты продавца (`seller_*` в `.env` прода) ждут реальных данных;
> на проде 0 организаций, поэтому реквизиты покупателя пока не наполнены.

**Цель:** менеджер выставляет счёт из заказа одной кнопкой, клиент скачивает и видит статус.

**Решения (утверждены в §16 п.40):**
- Invoice **1:1 с заказом** (unique FK); переоформление — вне этапа.
- Статусы `ISSUED/PAID/CANCELLED` переключает **менеджер вручную** — платёжного ledger нет.
- Номер: `СЧ-YYYY-NNNNNN` из PG-последовательности `invoices_seq_seq` (урок §9: sequence, не MAX+1).
- Валюта = `Order.currency_code` (заморожена в заказе).

- **Миграция (сделано, 0023)**: `invoices` (id, order_id UNIQUE FK, seq, issued_at, due_at NULL, total_amount Numeric(14,2), currency_code, status, pdf_status, version, created_by) + реквизиты в `organizations`: `legal_address`, `legal_phone`, `legal_email`, `bank_name`, `bank_code`, `bank_account` (УНП = существующий `tax_id`, отдельного поля `unp` нет — §16 п.40 п.4; TODO §16 п.25 закрыт).
- **Backend (сделано)**: `POST /api/v2/manager/orders/{id}/invoice` (Idempotency-Key, 201) → Invoice + Celery-рендер PDF (weasyprint, состояние в колонке `pdf_status`, не в Redis); `POST /api/v2/manager/invoices/{id}/pdf` (перерендер, 202); `PATCH /api/v2/manager/invoices/{id}` (статус, If-Match по `version` с аудитом `invoice.update`); `PATCH /api/v2/manager/organizations/{id}` (реквизиты, If-Match). Клиенту — блок `invoice` в `GET order detail` и в списке заказов. Скачивание PDF **байтами** через `GET /api/v2/orders/invoices/{id}/download` (никогда presigned — §16 п.37).
- **Frontend (сделано)**: `manager/orders/[id]` — панель счёта (выставить, смена статуса, перерендер, скачать, авто-опрос PENDING→READY); `orders/[id]` (клиент) — карточка счёта; `manager/organizations` + `[id]` — реквизиты.
- **PDF-шаблон (сделано)**: реквизиты продавца/покупателя, адрес доставки, позиции с замороженными ценами, итог, «Без выделения НДС», «цены зафиксированы и не пересчитываются», колонтитул «Стр. N из M».
- **Канон:** §5.2, §6, §10, §16 п.40 — коммит `5690a97` до кода (§21).
- **Приёмка (выполнена)**: параллельное создание не плодит дубли (unique FK + savepoint вместо отката транзакции роутера — иначе терялась бы резерв Idempotency-Key); повторный POST с тем же ключом → тот же счёт + `X-Idempotency-Replayed: true`; новый ключ на тот же заказ → 409 `INVOICE_ALREADY_EXISTS`; клиент видит только свой счёт, чужой → 404 без утечки существования; `If-Match` защищает от гонки правок.
- **Вне этапа:** платежи, акты сверки, дебиторка, онлайн-оплата.

## Этап 5. Скидки за объём — M

**Цель:** tiers «от N шт −X%», применяются автоматически в каталоге и корзине.

**Решения по умолчанию:**
- Tiers задаёт менеджер **на уровне бренда**: `brand_volume_tiers(brand_id, min_qty, discount_percent)`, uq (brand, min_qty).
- Применяется **лучшая подходящая** tier по qty строки; с `OrganizationBrandTerm` **не суммируется** — действует максимум из двух.

- **Backend**: PricingService + Redis-кэш с теговой инвалидацией при правке tiers (горячий путь — без кэша нельзя). В price-объектах v2 добавить `volume_tier` (применённая) и `tiers[]` (для показа «от N шт −X%»).
- **Frontend**: `manager/brands` — редактор tiers; карточка товара — бейдж «от 10 шт −2%»; корзина — расшифровка применённой скидки по строке.
- **Канон:** §7 (прайсинг) + §6.
- **Приёмка:** юнит-тесты PricingService на границах qty и пересечении с brand term; инвалидация кэша при изменении tier; e2e корзины.

## Этап 6. Согласование заявок в организации — M/L

**Цель:** заявки BUYER сверх лимита ждут визы OWNER.

- **Миграция**: `organizations` + `approval_mode (OFF/ALL/OVER_LIMIT)`, `approval_limit_amount Numeric NULL`; `orders` + `approval_status (NOT_REQUIRED/PENDING/APPROVED/REJECTED)`, `approved_by/at`, `rejection_reason`.
- **Флоу**: checkout → при ALL или (OVER_LIMIT и total > limit) и создатель не OWNER → order создаётся `PENDING` (менеджер видит с бейджем «ждёт согласования», не обрабатывает). `POST /api/v2/orders/{id}/approve|reject` — только OWNER, Idempotency-Key. APPROVED → обычный FSM; REJECTED → терминальный с причиной.
- **Уведомления**: in-app центр (pull) — работает уже сейчас; SSE не блокер (починка `publish_notification` — отдельная задача вне плана).
- **Frontend**: бейджи в списках заказов, кнопки визы в карточке (OWNER), настройки в `profile/organization`, статус в `manager/orders`.
- **Канон:** §5, §6, §16.
- **Приёмка:** граница лимита (равно/больше), только OWNER, повторный approve идемпотентен, уведомление создаётся.

## Этап 8. Коммерческие предложения — L  *(после Э4 — переиспользует PDF/seq-паттерны)*

**Цель:** менеджер собирает КП с нестандартными ценами и сроком действия; клиент принимает → заказ.

**Решения по умолчанию:** accept → сразу заказ (цены замораживаются из КП); КП видно клиенту в кабинете org-scope (без публичных токен-ссылок).

- **Миграция**: `quotes` (org, created_by, status DRAFT/SENT/ACCEPTED/EXPIRED/REJECTED, valid_until, seq, version) + `quote_items` (product, qty, unit_price, comment). Celery-beat помечает EXPIRED.
- **Backend**: manager CRUD + `POST .../quotes/{id}/send|accept|reject`; accept создаёт заказ (Idempotency-Key). PDF как у счёта.
- **Frontend**: `/manager/quotes` — конструктор из каталога с override цены; клиентская read-only `/quotes/[id]` + список в кабинете.
- **Канон:** §5, §6, §16.
- **Приёмка:** конвертация создаёт заказ с ценами КП; истёкшее КП не принимается (409).

## Вне плана (и почему)

- **Мульти-склад, lead time** — придут с реальной 1С-интеграцией.
- **Трекинг ТК** — требует продуктового выбора перевозчика.
- **Онлайн-оплата** — регуляторика/ERIC, отдельная инициатива.
- **Платёжный ledger, акты сверки** — после опыта эксплуатации Э4.
- **Задачи/рассылки менеджера** — низкий приоритет, по востребованию.
