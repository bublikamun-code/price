Полный функциональный прогон UI в настоящем браузере (Chromium 153 / Playwright)
по клиентскому и менеджерскому кабинетам: инвентаризация всех интерактивных
элементов на каждом экране и клик по каждому из них с фиксацией ошибок
консоли, сетевых ответов и реакции UI.

## Среда

- Стенд: docker `pp-*` (api/web/nginx/redis/db/rustfs), прод-оверлей, `https://localhost/price`.
- Браузер: Chrome for Testing 153.0.8010.12 (Playwright 1.63, chromium-1243), десктоп 1440×900 и мобильный 390×844.
- Роли: менеджер `manager@example.com`, клиент `client@priceweb.ru` (вход через настоящую форму).
- Данные стенда демо-стендовые: 4 пользователя, 30 товаров, 20 заявок.
- Метод: для каждого роута снимается статика (console errors, HTTP ≥ 400, битые картинки,
  горизонтальный оверфлоу, кнопки без доступного имени), затем по каждому видимому
  интерактивному элементу выполняется клик с восстановлением состояния страницы.
- Деструктивные кнопки (удаление, откат, сброс пароля, деактивация) кликались без
  подтверждения — по решению владельца от 2026-11-15.
- Инструмент прогона приложен: `docs/ui-audit/gui-audit.mjs` (основной обход) и
  `docs/ui-audit/gui-audit-targeted.mjs` (целевые проверки находок). Запуск:
  `node docs/ui-audit/gui-audit.mjs client|manager|public|mobile|extra` с
  `BASE`, `SHOTS`, `OUT` в окружении.
- После прогона стенд восстановлен: временная учётка `admin.audit@priceweb.ru` удалена,
  деактивированный прогоном клиент `client@priceweb.ru` снова активен (пароль сброшен
  менеджерским API, `must_change_password = false`).

## Разбор

### Разбор находок

Ниже — вердикт по каждой находке прогона: что это, где в коде, что видит пользователь и что
делать. Находки, помеченные «корректно», дефектами не считаются: их поведение проверено
в браузере и соответствует замыслу.

#### High

**H1. Счёт помечен «PDF: Готов», но скачать его нельзя.**

- Где: менеджерская страница заявки → блок «Счёт на оплату» → кнопка «Скачать счёт»
  (`apps/web/components/manager/OrderInvoicePanel.vue:311-324`).
- Что происходит: в БД `invoices.pdf_status = READY`, но `invoices.pdf_file_asset_id IS NULL`
  (счета `СЧ-2026-000002`, `СЧ-2026-000003`). Эндпоинт
  `GET /api/v2/orders/invoices/{id}/download` отдаёт `409 INVOICE_PDF_NOT_READY`, если
  `pdf_status != READY` **или** `pdf_file_asset_id IS NULL`
  (`apps/api/app/api/v2/invoices.py:345-353`).
- Что видит пользователь: зелёный бейдж «PDF: Готов», активная кнопка «Скачать счёт», после
  клика — красная плашка «Не удалось скачать счёт» без объяснения причины. Скачать счёт
  невозможно, перерендерить — нельзя (кнопка перерендера показывается только при `FAILED`).
- Скриншот: `gui-audit-screens/ui-audit-2026-11-15/findings/f1_manager_invoice_download_409.png`.
- Рекомендация:
  1. выяснить, кто проставил `READY` без asset — таска `export_invoice_pdf` ставит `READY`
     вместе с `pdf_file_asset_id` в одной записи (`apps/api/app/tasks/export_invoice_pdf.py:110-111`),
     значит состояние пришло из обходного пути или из данных, созданных до текущего кода;
  2. добавить в эндпоинт скачивания отдельный код для «файл счёта отсутствует» (сейчас тот же
     409, что и «ещё рендерится») и различать их в UI;
  3. показывать в панели счёта состояние «Файл счёта не сформирован» + кнопку «Перерендерить
     PDF», когда `pdf_status = READY`, а файла нет.

**H2. Менеджер на клиентских страницах получает `403` на корзину, но видит её элементы.**

- Где: `apps/web/pages/profile/index.vue:5`, `profile/notifications.vue:2`, `profile/sessions.vue:4`
  — все три используют `layout: 'client'`; клиентский layout поднимает корзину
  (`apps/web/components/layout/ClientHeader.vue:4` → `useCartV2` → `GET /api/v2/cart`).
- Что видит пользователь: в шапке плашка «ТЕКУЩАЯ ЗАЯВКА · 0 позиций» и пункт меню
  «Текущая заявка», при этом запрос `GET /api/v2/cart` для роли MANAGER отклоняется с `403`
  (в консоли — ошибка на каждой загрузке `/profile*`). Текст на самой странице профиля прямо
  признаёт: «Контактные данные и ФИО изменяет менеджер: в клиентском кабинете
  соответствующего запроса пока нет».
- Скриншот: `gui-audit-screens/ui-audit-2026-11-15/findings/f3_manager_profile_cart_403.png`

- **Пункт «Администрирование» (было M1) — ложное срабатывание самого аудита.** Меню
  менеджера уже скрывает пункт для не-ADMIN: `v-if="auth.isAdmin"` в обоих местах

  прогона. HTTP 403 в отчёте — результат **прямого захода** на `/manager/admin` из списка
  маршрутов аудитора, а не клика по меню: для роли MANAGER страница закрыта middleware

  плашку «Действие не выполнено. Ожидалась версия 2, актуальная версия 88» с кнопкой

  заявки была разогнана предыдущими деструктивными кликами прогона по статус-кнопкам.

#### Замечания к инструменту прогона (не дефекты приложения)

- `net::ERR_ABORTED` / `net::ERR_FAILED` / `net::ERR_NETWORK_CHANGED` — следствие того, что
  после клика страница перезагружается для восстановления состояния; обрывается SSE-поток
  уведомлений и незавершённые запросы. В замечания не вынесены.
- `net::ERR_NETWORK_CHANGED` на `/api/v1/notifications/stream` — то же самое.
- «Элемент исчез после предыдущего действия» — элемент списка исчез после того, как
  предыдущий деструктивный клик изменил состав списка (например, удалил строку). Пропуски
  считаются ожидаемыми.
- `make ratelimit-reset` на стенде не отрабатывает: цель вызывает `$(DC) exec -T redis`,
  а на этом стенде сервис называется `pp-redis` (compose-проект поднят с другим именем) —
  команда падает с «service "redis" is not running». Счётчики логина пришлось сбрасывать
  вручную: `docker exec pp-redis redis-cli --scan --pattern "LIMITS:*auth/login*" | xargs -r
  docker exec pp-redis redis-cli DEL`. Сама цель корректна для дев-стека из `make up`.
- Rate-limit входа — 5 попыток за 15 минут на IP: при прогоне нескольких кабинетов подряд
  (менеджер → клиент → админ) счётчик исчерпывается. Для проверок вручную это заметно.

#### Ограничения прогона

- Проверялись 49 экранов (16 клиентских, 20 менеджерских, 2 доливочных, 15 мобильных,
  8 публичных — с учётом перекрытий) и около 1000 кликов. Набор страниц взят из
  `SITEMAP.md` §4 и `apps/web/pages/**`; страницы с параметром (`[id]`, `[sku]`) открывались
  по первой доступной записи из списка.
- Мобильный проход — 390×844 (`isMobile`, `hasTouch`) на тех же десктопных маршрутах плюс
  мобильные экраны `/m/*`.
- Не покрыто: работа в реальном 2FA-клиенте (TOTP), отправка писем (очередь `email_outbox`
  проверялась косвенно), сценарии загрузки файлов в S3 из UI (файл-архив проверен на
  существующих объектах), TG Mini App (отдельный layout, вне объёма кабинетов).
- Стенд — демо-данные: 30 товаров, 1 серия, 4 учётки, 20 заявок; часть находок (например,
  H1) связана с состоянием конкретных демо-записей и требует проверки на чистых данных.
